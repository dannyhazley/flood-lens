### C0 build guide — a project foundation you can reuse

This guide expands the ordered tasks above. Your deliverable is a small Python project whose quality checks run locally and in continuous integration. **CI belongs here from the start.** Remote execution can be verified later if you deliberately keep the repository local, but the workflow definition and local equivalent are part of C0, not a vague future improvement.

#### Understand the parts before creating files

- **Repository:** the files and their version history. Use one default branch, normally `main`, and short feature branches for bounded changes.
- **Package:** importable code under `src/floodlens/`. A source layout helps catch accidental reliance on the working directory. Installing the package should make it importable from elsewhere.
- **Environment:** Python and the dependencies actually installed for this project. uv creates/manages it; `pyproject.toml` declares the project and dependency groups; `uv.lock` records the resolved combination. Pin one supported Python minor version after checking the actual machine, rather than testing an imaginary matrix immediately.
- **Test:** an executable check of observable behaviour. At C0, check package import/version and the minimal command’s success/failure behaviour. Add scientific fixtures at C1, when there is scientific behaviour to test.
- **CI:** a clean automated runner repeats the checks when code changes. This catches “works only in my old terminal”.
- **Continuous delivery:** a passing revision can be packaged into a reproducible candidate. **Continuous deployment:** a passing revision automatically changes a running service. C0 establishes CI and a delivery design; it does not deploy software. The later release pipeline is specified below.

#### Create these artifacts in this order

| Artifact to create later | What belongs in it | How you know it is useful |
|---|---|---|
| `README.md` | Problem, real status, supported environment, install/check instructions and next checkpoint | Someone can tell what exists and repeat the smallest check |
| `.gitignore` | Raw/local data, weights, run outputs, virtual environments, caches and secrets | Git’s staged list contains intentional source/configuration only |
| `pyproject.toml` | Package name, supported Python, build backend, minimal runtime dependencies, development group and Ruff/pytest configuration | A clean environment installs the package and resolves test tools |
| `.python-version` or equivalent documented runtime choice | One compatible Python minor version | Local and CI environments agree on the declared runtime |
| `uv.lock` | The resolved environment produced from project metadata | A locked/frozen install works without rewriting it |
| `src/floodlens/__init__.py` and a minimal command module | Package identity/version and one useful entry point | Installed imports and the command work outside the repository root |
| `tests/test_package.py` / command smoke test | Import/version and actual documented command behaviour | A missing module or broken entry point fails clearly |
| `.github/workflows/ci.yml` | The CI specification described below | Its checks match the local quality commands |
| `docs/development.md` | Branch → local checks → PR/review → merge → release routine; CI failure diagnosis | You can repeat the routine on another project |
| Progress/checkpoint/decision notes | Actual time, revision, checks, blockers and one next step | A later session resumes without rebuilding context |

Do not fill `src/` with empty architectural layers yet. A small package plus a meaningful smoke check is enough to establish the pattern. The future CLI can start with Python’s standard `argparse`; add a richer CLI library only if the command hierarchy actually becomes awkward.

#### Concrete C0 tool choices and core operations

Use **uv** for the environment/lock/build workflow, **Hatchling** as a small Python build backend (or retain the compatible backend generated by the chosen package scaffold and document it), **pytest** for behaviour, and **Ruff** for lint/format. C0 runtime can remain standard-library-only. Put development tools in a development dependency group; a build-backend dependency belongs to the build-system configuration, not the eventual inference runtime.

| Core operation | What you use it for | Expected result |
|---|---|---|
| uv `init` / `venv` / `sync` / `run` / `build` | Initialise only if absent, manage isolated dependencies, execute within that environment and build the package | Repeatable installed project; lockfile does not drift during CI |
| Standard `argparse.ArgumentParser`, `parse_args` | Minimal command help/version/options | Help/version exits successfully; unsupported arguments fail clearly |
| `importlib.metadata.version` | Read installed distribution identity | Installed wheel version is available outside the source checkout |
| pytest `tmp_path`, `raises`, `mark.parametrize` | Temporary output locations, expected failures and a few meaningful input variants | Tests do not write to real data directories or rely on hidden local files |
| Ruff `check` / `format --check` | Code correctness/style feedback and format verification | CI fails for a real violation and never silently edits source |

The first test should exercise a real user/package boundary: the documented version/help command from an installed package, including its exit behaviour. Avoid writing a dummy mathematical test merely to make a badge green.

#### What exactly goes into the first CI workflow

Use **GitHub Actions** as the default for a GitHub repository. No YAML is supplied here: the table is the specification you should turn into the workflow during implementation. The cloud runner only sees committed files, so anything it needs must be versioned or deliberately installed.

| CI element | Include at C0 | Reason / expected outcome |
|---|---|---|
| Triggers | Pull requests targeting `main`, pushes to `main`, and manual dispatch | Review changes before merging and verify the actual merged revision |
| Runner/runtime | One hosted Linux runner and the declared Python minor version | A fresh independent environment; native macOS tests remain local until a real portability need appears |
| Checkout | Official checkout action, version pinned/reviewed at implementation time | Runner receives the intended commit; do not depend on files on your laptop |
| Environment setup | Official uv setup integration, reviewed/pinned action reference, then locked install including development tools | Same dependency policy locally and remotely; use its supported frozen/locked mode |
| Lint | Ruff check with a modest initial rule set: errors and Pyflakes/unused imports; add stricter rules deliberately | Undefined/unused/problematic code fails without requiring a huge style project |
| Formatting | Ruff format in check-only mode | CI reports formatting differences instead of secretly changing source |
| Tests | pytest, with JUnit results written to a report directory | Package/command behaviour is checked and failures can be inspected |
| Packaging smoke check | Build the Python distribution, then install the built wheel into a separate temporary environment and import/run its entry point | Editable development installs can hide missing packaged files; this catches that problem early |
| Results | Upload small test reports and wheel/build artifacts on appropriate outcomes; use a short retention such as seven days | Keep diagnostic evidence; never upload raw data, secrets or large weights |
| Bounds | A short job timeout, proposed ten minutes, and cancellation of superseded runs on the same branch | A hung command cannot consume unlimited runner time; measure normal duration before adjusting |
| Permissions | Read-only repository contents for CI; no deployment secret or broad write token | These checks need to read/build/test, not publish or alter infrastructure |
| Failure policy | Any failed quality/packaging step fails the job; report upload may still run after test failure | A green badge must mean the actual checks passed |

The local equivalents are uv’s environment/run/build operations, Ruff’s `check` and `format --check`, and pytest with JUnit reporting. Learn what each command does rather than remembering one long shell line. Select actual action references and dependency versions from official documentation when implementing; this manual does not claim an untested combination works.

#### Translate the specification without guessing configuration names

The workflow concepts correspond to GitHub’s `on` triggers, `jobs`, `runs-on`, `steps`, `permissions`, `timeout-minutes` and `concurrency`. A step either `uses` a reusable action or `run`s a command; `with` supplies an action’s supported inputs. The named actions are `actions/checkout`, `astral-sh/setup-uv` and `actions/upload-artifact`; choose reviewed/pinned references when implementing. Do not copy an old action version from memory.

The Python quality operations to reproduce locally are `uv sync --locked`, `uv run ruff check .`, `uv run ruff format --check .`, `uv run pytest --junitxml=reports/pytest.xml`, and `uv build`, with the selected development group installed. These are tool operations, not application code. The wheel-install smoke check needs a **separate** temporary environment and installation of the built wheel; running another editable import from the same working tree would not check packaging. Capture command/output and explain a nonzero exit before marking the step done.

At later checkpoints, install only the dependency groups/extras actually used by that job. A CPU fixture test should not require a GPU runner or downloaded weights. Distinguish environment cache from source/model provenance; a cache speeds installation but is never the only record of an input.

#### Prove that CI means something

1. Run each local check separately so you recognise lint, format, test and package failures.
2. Install the built wheel in a temporary environment and execute the documented command from a different directory. Success must not depend on `src/` being on your shell path.
3. Make a temporary local change that breaks the command’s expected exit behaviour; observe the existing smoke check fail, then restore it. Do not keep a contrived failing test or throwaway branch as project clutter.
4. When a private remote is deliberately created and pushing is authorised, run the workflow and save its URL/commit/status. A private remote is still external storage; do not push data or employer material merely to get a green badge.
5. Make passing CI a merge requirement where repository settings/account permissions support it. Otherwise document that this is a manual discipline. Do not claim enforced branch protection when only a README rule exists.
6. Record **configured locally**, **executed remotely** and **merge rule enforced** separately. A workflow file sitting on disk is not proof GitHub has run it.

If CI fails, classify it before changing packages: checkout/environment problem, dependency install problem, lint/format problem, behaviour failure or packaging failure. Read the first failed step and its real error. Reproduce that one step locally. If local passes but Linux fails, inspect case-sensitive paths, working-directory assumptions, native dependencies and runtime versions. Do not fix a red build by ignoring its check.

#### How CI/CD grows through the project

| Checkpoint | Add to automation when the behaviour exists | Keep outside routine CI |
|---|---|---|
| C1 | Synthetic raster/mask/grid validation tests | Real dataset acquisition and rights approval |
| C2 | Group-leakage and hand-counted metric/baseline checks | Reserved-event evaluation |
| C3 | Tiny CPU forward/loss/artifact-reload tests, using synthetic input | Full neural training, GPU trials and scientific performance promises |
| C4 | Report-schema/count/coverage consistency checks | Automatic retuning or test-set-based model promotion |
| C5 | Geographic export round trip and malformed-input rejection | Full collection processing |
| C7 | API contract, job transition and interruption/recovery checks | Running a public worker on untrusted input |
| C8 | Frontend type check, production build and a small Playwright journey | Every possible browser/device configuration |
| C9 | Candidate release build, fixture inference, checksums, report and dependency record | External publication and operational deployment unless separately chosen |

**C9 delivery design:** a manually invoked release-candidate job receives a chosen revision/model ID, runs the checks, builds the wheel and web assets, validates a tiny allowed inference example, and assembles a candidate bundle with checksums/version metadata. It stops with a downloadable artifact. If hosting is later chosen, a separate environment-gated deployment job uses approved credentials, verifies health/smoke checks and records rollback to the previous artifact. Never deploy newly trained weights simply because a training run ended. Packaging, publication, hosting and operational deployment are distinct evidence states.
