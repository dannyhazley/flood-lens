# Checkpoint 1 — Data rights, provenance and raster-quality audit

**1. Purpose:** Find out what the proposed data actually measures and whether it is usable for this project before modelling.

**2. Applied question:** Can these observations and labels support a traceable observed-water layer for the intended portfolio use?

**3. Why this matters:** A model cannot fix unclear label meaning, unusable rights, missing observations or geographic misalignment. The existing evidence is metadata research, not raster validation.

**4. Concepts before starting:** Raster, radar backscatter, bands/units, label taxonomy, nodata, validity masks, CRS, affine transform, alignment, manifest/checksum and provenance. Read note 02 and the matching entries in note 22.

**5. Exact ordered tasks:**

1. Phase A, 3–4 h: read the provider documentation and saved audits. Separate code, imagery, annotation, derived-output and model-artifact terms. Write the intended use and documented proceed/replacement decision in `docs/data-card.md`; retain unresolved evidence. Do not treat a repository badge or a mirror as a definitive annotation grant.
2. If rights/access cannot be established, use this phase to assess a bounded replacement against note 03. Record rejection and the exact missing evidence. Do not send provider enquiries automatically or proceed on assumed rights.
3. Phase B, 8–9 h: after approval, retrieve only a small representative sample with source URLs, retrieval dates, byte counts and SHA-256. Start with one image/label pair, then at least one chip per reconciled event. Keep raw assets ignored. Deduplicate catalogue hrefs before counting or downloading.
4. Print actual dtype, dimensions, band order, units, finite ranges, CRS, transform, footprint, nodata and label codes. Confirm image/label grid agreement and inspect an aligned overlay. Keep display stretching separate from sensor values. Read masks explicitly; do not infer validity from brightness.
5. Validate every asset in the selected subset automatically. Distinguish metadata checks over an inventory from pixel checks over downloaded assets; report both coverage denominators. Use synthetic wrong-grid, bad-class and all-invalid cases to prove rejection. Do not download the entire collection merely to finish this phase.
6. Phase C, 6–7 h: reconcile filenames, event metadata and acquisition siblings, including the Mekong/Cambodia alias. Produce event counts, valid coverage, label prevalence and band distributions for the audited subset. Record accepted, flagged and excluded scenes with reasons; do not silently drop difficult scenes.
7. Write the audit findings, limits and affordable next acquisition plan. Explain one accepted scene and one defect/rejection. Source collection expansion is a later controlled action under the same manifest, not evidence that uninspected rasters already passed.

### C1 build guide — from source bytes to an auditable raster

Work through one approved pair before batching. **Inputs:** provider records, source raster, label raster and terms evidence. **Output:** an accepted/flagged/rejected manifest record plus a reproducible overlay and validation report. No model is involved.

#### Libraries and the core operations

| Use | Library / API to learn | Input → result and rule |
|---|---|---|
| File identity | Standard `pathlib.Path`, `hashlib.sha256`, `json`, `csv` | Local file bytes → stable hash/metadata record; hash in chunks rather than reading a large raster entirely into memory |
| Controlled retrieval | `httpx.Client` / streamed response; `raise_for_status` | Approved URL → temporary file, status/byte count/hash; use explicit timeouts and bounded retries, then finalise only on success |
| Read raster | `rasterio.open`, dataset `read`, `count`, `dtypes`, `descriptions`, `crs`, `transform`, `bounds`, `res`, `nodata` | File → numeric array and geographic metadata; Rasterio band indices start at one, NumPy axes at zero |
| Source validity | Dataset `read_masks` plus `numpy.isfinite`, `numpy.all` | Per-required-band masks/ranges → one source-valid boolean grid; require all required bands, not merely any band |
| Label validity | `numpy.unique`, explicit class comparisons | Reference array → verified class inventory and valid-label grid; an ignore code is not a negative class |
| Distributions | `numpy.count_nonzero`, `numpy.percentile`, `numpy.mean`, `numpy.std` | Valid values only → coverage/prevalence/range summary; empty selections must be flagged before reduction |
| Pixel/world checks | Dataset `xy` / `index`, `rasterio.transform.xy` | Pixel row/column ↔ centre coordinate; record the CRS and compare known locations |
| Audit plots | `matplotlib.pyplot.subplots`, axes `imshow` / `hist`, figure `savefig` | Same-grid arrays → labelled saved panels and distributions; display contrast never modifies model input |
| Controlled alignment when justified | `rasterio.warp.reproject`, `Resampling.nearest` for labels | Original grid + explicit destination grid → derived asset with recorded transformation; do not repair by array resizing |

The dataset-wide `dataset_mask` can combine band information differently from a required-band logical AND. For a two-band model, inspect per-band `read_masks` and verify both required bands are valid. A source pixel can be observed even when no manual label exists.

#### Suggested functions you will build, not existing APIs

| Proposed project function | Responsibility | Outcome to verify before the next function |
|---|---|---|
| `hash_asset` | Stream bytes and return SHA-256/byte count | Same unchanged fixture has the same hash; one changed byte changes it |
| `inspect_raster` | Read metadata, masks and permitted summary statistics without changing bytes | A human-readable record names every band, grid and missingness convention |
| `validate_pair` | Compare pairing IDs, CRS, transform, dimensions, masks and label codes | Correct pair accepted; same-size shifted pair rejected with a specific reason |
| `build_validity` | Return source-valid, label-valid and evaluation-valid separately | Synthetic example below gives exactly the expected three/two valid counts |
| `write_audit_report` | Combine accepted/rejected records and figures | The report’s denominators match its manifest and every exclusion has a reason |

Keep these functions small enough to inspect independently. File I/O, numerical validation and report rendering should not be one opaque notebook cell.

#### Walk one pair through the process

1. Record approval scope and exact source/label IDs. Retrieve only approved assets into the ignored cache, using a temporary filename until the response completes. Save retrieval time separately from acquisition time.
2. Open both files and record their metadata before applying any processing. Confirm provider band names/units with the actual values and metadata. Do not guess VV/VH order from an array’s shape.
3. Compare CRS, height/width, transform and bounds. Establish a small documented tolerance for floating metadata comparisons; explain it in metres/pixels where possible. Metadata agreement does not prove the original annotation is physically correct, so inspect an overlay too.
4. Build the three masks. Quantify valid source pixels, valid labels, valid evaluation support and water prevalence on that support. Reject unexpected class values.
5. Save a three-panel source/label/validity visual with acquisition date, scene ID and a legend. Stretch radar for visibility only on a copy.
6. Run synthetic failures before scaling to the event-diverse subset. Summarise by actual reconciled event, not by raw filename count.
7. Produce a report that lets another person explain which assets passed and exactly what has not yet been audited.

**Teaching example:** imagine four pixels in a 2 × 2 grid. The first three have valid radar input; the fourth does not. Labels in reading order are water, non-water, ignore, non-water. Source-valid count is three; label-valid count is three; evaluation-valid count is **two**, the first two. The third pixel can receive inference but cannot be scored; the fourth cannot receive supported inference even though it has a label.

For a geographic fixture, use an explicitly synthetic projected grid with corner origin (500000 m, 6000000 m), 10 m pixels and rows running southward. The top-left pixel centre is (500005 m, 5999995 m). Shifting the origin 10 m east moves every cell one pixel even though its array size stays the same. `validate_pair` must detect this. This demonstrates geometry, not an actual flood location.

**Debugging order:** unreadable file → wrong metadata/units → wrong pairing/grid → masks/classes → plotting. A strange plot can be a display stretch, but wrong numerical metadata cannot be repaired by prettier colours. Do not continue to ML until you can explain one real accepted pair and the synthetic failures.

**Teaching/repetition exercise:** recreate the four-cell source/label/evaluation mask counts on paper without consulting the answer; explain how an equal-size shifted grid fails. Then describe the equivalent missingness/pairing checks for a table of sensor observations.

**Repeatable pattern:** immutable input → inspect → validate → record decision → report. On a later medical/table/sensor project, the validation rules change but this sequence and the separation of source versus reference missingness remain useful. Add the synthetic invariants to CI; do not put approved raw imagery into the runner.

**8. What can go wrong:** Treating proprietary metadata as settled permission or settled prohibition; decoding dB as linear values; counting duplicate catalogue links; merging event names by guess; counting nodata as dry; making class labels fractional through resizing.

**9. Genuine blocker:** Missing usable terms, inaccessible assets, unrecoverable spatial metadata, contradictory label meaning or unresolved group identity prevents a defensible source decision. A completed rejection report is useful but does not pass the dataset gate.
