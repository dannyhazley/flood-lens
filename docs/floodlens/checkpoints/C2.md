# Checkpoint 2 — Event-aware evaluation design and simple baseline

**1. Purpose:** Define a fair test and build a simple water-mapping reference before investing in a neural model.

**2. Applied question:** How well does a simple method work on development events, and what would count as evidence about unfamiliar events?

**3. Why this matters:** An attractive prediction and a random pixel split can hide leakage. A baseline makes added complexity falsifiable and gives the first useful release at 40–55 total hours.

**4. Concepts before starting:** Event/group split, event holdout, leakage, baseline/Otsu, IoU, precision/recall, macro versus pooled scores and development versus final-test roles. Read note 11 before writing the protocol.

**5. Exact ordered tasks:**

1. Phase A, 6–8 h: extend acquisition only to the approved, bounded experiment inventory. Apply C1 validation to every asset admitted to training/evaluation, estimate storage/compute, and keep inventory changes versioned. If this cannot fit, reduce the declared study or re-estimate; do not claim the whole source was audited.
2. Reconcile event episodes, overlapping footprints, repeated acquisitions and related weak labels into groups. Check file hashes and spatial/time overlap. Propose 7 training/2 development/2 final events only if the audited identities and coverage support it; otherwise record a justified design.
3. Save immutable group assignments and protocol before tuning. Define eligible pixels, primary macro event water IoU, secondary counts/precision/recall/F1, pooled scores, empty-union convention and all-invalid handling. Log permitted pre-split integrity inspection. Keep final-test model outputs hidden.
4. Define the baseline band, units, histogram mask, Otsu/fixed-threshold scope, water side and any postprocessing. Per-scene Otsu can use unlabelled scene statistics if predeclared. Fit learned preprocessing/thresholds on training/development only. Published-split reproduction is optional and deferred until the main final results lock.
5. Phase B, 8–12 h: implement the baseline and dry-prediction sanity check. Verify hand-calculated confusion examples, empty/no-water cases, invalid pixels and duplicate-window accounting. Run on development events only for selection/demonstration.
6. Phase C, 6–10 h: regenerate predictions and reports from the saved configuration. Show one easy and one poor development example with date, valid coverage and score. Compare per-event and pooled summaries and explain why they differ.
7. Close C2 with the frozen protocol, rerun instructions and a go/narrow/stop decision. Begin C3 only if rights, grouping, validation and baseline execution are defensible.

### C2 build guide — split first, then a numerical reference

Your first ML-related deliverable is a valid experiment contract, not a neural network. Use Python/NumPy for transparent counts, scikit-image for the threshold operation, and saved CSV/JSON tables for results. A notebook may explore training/development material, but the final baseline command must not require its hidden state.

#### Define and inspect the tables

- **Scenes:** one row per accepted image/label pairing, with `scene_id`, reconciled event/overlap group, acquisition interval, footprint, source/label hashes and audit status.
- **Groups:** one row per independence unit with its scenes, geographic/time relationships and assignment rationale.
- **Splits:** group ID → training/development/final role, plus protocol version/hash. Every scene inherits its group’s role.
- **Results:** method/run/event IDs, TP/FP/FN/TN, valid pixels, reference-water pixels, IoU/precision/recall/F1 and warnings. Aggregates are generated from these rows, not typed manually into a slide.

An event name is not enough if separate names cover overlapping acquisitions or the same episode. Merge/reconcile related observations before partitioning; retain the original IDs. If geographic footprints cannot be reconciled, explain why the proposed independent-test claim is blocked.

#### APIs and functions to introduce

| Operation | Tool/API | Exact purpose and outcome |
|---|---|---|
| Table loading | Standard `csv.DictReader` / `json.load`; pandas only if its table operations help | Manifest → explicit records; fail on missing group IDs rather than silently filling them |
| Reproducible grouping | Python dictionaries/sets and a saved explicit assignment | One group has exactly one role; verify train/development/final sets are disjoint |
| Optional grouped folds | `sklearn.model_selection.GroupKFold` or `GroupShuffleSplit` | Training-group development/folds if required; these do not automatically create the intended final event allocation or detect geographic overlap |
| Threshold | `skimage.filters.threshold_otsu` | One declared band’s valid unlabelled values → scalar intensity threshold; record band, units, histogram construction and water direction |
| Classification | NumPy boolean comparisons | Threshold + valid image → water mask; invalid cells stay unavailable |
| Metric counts | `numpy.count_nonzero` with boolean masks | Common eligible pixels → TP/FP/FN/TN; derive scores explicitly |
| Independent count check | `sklearn.metrics.confusion_matrix` with fixed class ordering | Check your hand-counted counts; do not let absent classes change matrix interpretation |
| Figure/report | Matplotlib and saved tables | Development prediction/reference/error panels with dates, roles and coverage |

**Proposed project functions:** `freeze_group_split` validates and saves the assignment; `assert_split_integrity` checks duplicates/related groups; `predict_otsu` returns class/validity plus the chosen threshold; `confusion_counts` returns integer counts; `summarise_events` produces per-event and macro/pooled summaries. These names describe responsibilities you will implement later, not functions already provided by a package.

#### Build in this order

1. Create a five-record synthetic grouping table: Alpha has two scenes, Beta two, Gamma one. Put both Alpha scenes together. Deliberately assign one Alpha scene to training and its sibling to final in a temporary fixture; your integrity check must fail. Add an overlapping-footprint relationship even when names differ and verify it also prevents independent assignment.
2. Freeze the real eligible inventory and group mapping. Choose event roles before model scores exist. Explain the proposed 7/2/2 allocation or the justified replacement; save permitted integrity-inspection scope.
3. Write the metric conventions before predictions: all-invalid is unscorable; precision/recall zero denominators are undefined under the current policy; empty water union follows the declared convention and is separately flagged.
4. Build a declared fixed-threshold teaching example first so you can predict its answer by hand. For synthetic dB values -22, -20, -5, -3 and threshold -12, low-backscatter-as-water predicts the first two as water. This is only a software/intuition fixture, not a real radar decision rule.
5. Introduce Otsu using valid raw values from the chosen band. Record the resulting threshold per scene if adaptation is per scene. Handle constant-valued/no-valid input explicitly; a two-class histogram assumption can fail, so do not manufacture a confident result from it.
6. Score development events on exactly the same valid support intended for neural comparison. Aggregate each event’s counts before its IoU. Average event IoUs equally for the macro score; pooled counts give a different measure.
7. Regenerate the report from a saved configuration and compare the rerun. Save an easy and poor development example by a stated rule; retain every event row.

**Hand calculation you should be able to explain:** using the C1 four-pixel example, predict water at the first three locations. Only the first two locations are scored: TP=1, FP=1, FN=0, TN=0. IoU=1/2, precision=1/2, recall=1, F1=2/3. A metric scoring all four cells has used the wrong support, even if its final percentage happens to match the eligible-pixel result. If two events have IoUs 0.9 and 0.3, the macro event IoU is 0.6 regardless of their different pixel counts.

**What to put in CI now:** synthetic group separation/duplicate detection, known confusion counts, empty/invalid cases and reproducible baseline behaviour on a tiny synthetic raster. CI should not download the dataset, reveal reserved results, or require a neural model.

**Teaching/repetition check:** explain why a pixel-random split can answer a different question from event holdout. Then design a grouped split for patients with multiple scans or factories with multiple sensor windows. Reuse the independence reasoning; do not reuse flood-event names or assume the same 7/2/2 ratio is universally appropriate.

**8. What can go wrong:** Random tile splitting; fitting normalisation on all events; treating a weak algorithmic label as independent truth; cherry-picking a favourable split; counting overlapping output windows twice; reproducing a published training split that contaminates the primary final events.

**9. Genuine blocker:** No defensible independent groups, unavailable required labels, persistent wrong metric counts or unaffordable accepted inventory. A low baseline score is a finding, not a blocker or proof a neural model will help.
