# Checkpoint 9 — Hardening, reproduction, demo and final case study

**1. Purpose:** Verify the complete product, measure the bounded analyst workflow and prepare an honest final evidence pack.

**2. Applied question:** Can someone reproduce it, and does its workflow improve the defined inspection task compared with manual review?

**3. Why this matters:** Engineering completeness and decision value need evidence beyond a successful demo. A measured negative result is stronger than an untested benefit claim.

**4. Concepts before starting:** Reproduction versus deployment, quality-constrained workflow comparison, paired task results, participant/order bias, release provenance and supported public claims. Read note 09 protocol and note 14 interview guidance.

**5. Exact ordered tasks:**

1. Phase A, 10–15 h: use a clean checkout/environment or a willing reviewer to follow the actual README. Reproduce one inference artifact, document the separate training path, and exercise failures, restart, exports and browser journeys. Fix critical defects before a release.
2. Execute the frozen manual-versus-assisted study on the same small packets/assets/brief rubric. Use development/demo material, not new model tuning from final-test failures. Record first usable result time, active/wait time, scene count, repeated-run consistency, uncertain-area recognition, overlay accuracy, reproduction and report completeness.
3. Counterbalance order where possible, record operator experience/practice/caches and all errors/omissions, and retain failed/slow runs. A solo developer study is labelled self-study. No participant is contacted or recorded without their agreement; a second reviewer is optional.
4. Phase B, 8–10 h: analyse paired packet results and quality failures under the predeclared criterion. State improvement, tradeoff, no difference or invalid test as supported. Do not turn speed on easy scenes into business value or incident outcomes.
5. Finish README, data/model cards, architecture/decisions, actual hours/compute, study raw records and limitations. Write the case study from question through baseline/model result, failure, transfer, geographic outputs and workflow outcome.
6. Phase C, 7–10 h: save a local version/tag, demo/screenshots, final evidence index and proposed portfolio/LinkedIn material. Audit every headline against an artifact and label local/reproducible/hosted status accurately.
7. Review intended code/data/model/output sharing rights. Optional hosting requires a concrete cost/access/retention plan and an actually tested remote path under a separate explicit decision; it is not required for completion. Publication remains a separate future action.
8. Update state and retrospective with completed capabilities, unmet claims, total actual hours, unresolved risks and one bounded next decision. Do not mark a capability done solely to finish the route.

### C9 build guide — reproducible delivery and measured usefulness

The last checkpoint is not just “polish and publish”. It is a controlled reproduction, a quality-constrained human-task comparison and a versioned delivery candidate. Use the existing tools rather than introducing a final platform rewrite.

#### Prepare a candidate before measuring the task

Choose one revision and trusted method artifact; record dirty status, dependency locks, source/asset hashes and actual operating limits. Complete critical geographic/state/export fixes before scored workflow runs. Save any later defect corrections with their effect on comparability; do not mix multiple UI versions invisibly in the study.

Reproduce from an isolated environment with only the documented inputs and approved artifacts. Build/install the wheel, build the frontend, run the service/worker, and follow both journeys. If using a container, it packages the environment; it does not supply missing data rights, model provenance or identical cross-device numerical behaviour. Training reproduction is separately documented and measured; inference reproduction should not require rerunning the whole experiment search.

#### Implement the measurement sheet, not a benefit claim

| Record/API | What to capture | Verification |
|---|---|---|
| Standard `time.perf_counter` / explicit task timestamps | Start, first usable brief, active effort, processing/wait time and stop reason | Timing boundaries follow the frozen protocol in both modes |
| `csv.DictWriter` / structured task records | Packet/mode/order/operator/version, scene count, errors/omissions, uncertainty recognition, overlay/report/reproduction checks | Every scored attempt has a row, including failure/timeouts |
| NumPy/pandas paired summaries | Absolute paired packet times/counts and quality differences | No hidden deletion of inconvenient cases or criterion changes |
| Checksums and numerical comparison | Repeated-run class/validity arrays, canonical metadata and probability tolerance | Compare scientific content separately from timestamps/run IDs |
| Human rubric | Geography, dates/sources, missingness, candidate IDs, caveats and verification actions | A faster brief that fails a critical item is not a usable first result |

Run the practice packet first. Follow the manual and assisted routes using identical assets/task outputs and recorded order/caches/experience. A participant building the tool is a biased self-study, so say so. An independent reviewer is useful if available, but no imaginary users or quotes belong in the report.

**Worked interpretation example:** if manual review takes 18 minutes and assisted review 12 minutes on one synthetic packet, that is six minutes less for that packet only. If assisted review misses an uncertain region required by the rubric, the faster result may fail usability/quality criteria. Neither observation establishes commercial savings or emergency-response impact. Keep absolute times, error counts and setup/training effort visible.

#### Assemble the delivery candidate

The C0 CI/CD design now matures into a manually selected **release-candidate workflow**. Run existing checks, build wheel/web assets, install the wheel in a clean environment, execute tiny permitted fixture inference and both essential journey checks, then assemble artifacts. Include revision/environment/dependency record, input/model/config IDs, checksum list, reports/cards, supported commands, limits and rollback/reproduction instructions. A build artifact is not automatically a GitHub release or deployment.

**Proposed project functions:** `verify_release_manifest`, `compare_reproduced_outputs`, `summarise_workflow_study`. Reuse the existing output validator rather than inventing a weaker release-only check. Make a claim-to-evidence table linking every headline to a run/report/test and its limitations.

If hosting is separately chosen, define a target environment and access/cost/retention limits; deploy the already reviewed artifact, run health plus a tiny approved analysis, and record its actual URL/date. Exercise rollback to the prior version and confirm jobs/data are handled safely. No cloud account/provider is selected by this manual. Avoid automatic deployment on every push and never auto-promote a model based on final-test scores.

#### Finish with evidence you can explain and repeat

Walk a reviewer through question → data gate → split → baseline/model result → failure → geographic output → asset review → workflow measurements → limitations. Give the actual study result, including no gain or a quality tradeoff. Explain the difference between local reproduction, hosted demo and an operational deployment with accountable users/service duties.

**Teaching/repetition exercise:** sketch a new project’s first CI-to-artifact path and identify the task-specific tests/labels you would replace. Save a small personal starter checklist for your next project: scope/claims, environment/CI, provenance, independent evaluation, artifact contract, reproducible inference, job state, UI journeys and measured user task. Keep FloodLens-specific models/data definitions separate from that reusable engineering pattern. This is a learning artifact in the existing checkpoint report, not a new generic framework to build.


**6. Expected files and evidence:** Clean-install/reproduction record, `docs/workflow-study/task-results.csv`, `docs/decision-value-results.md`, final README/cards/release notes/case study, demo, actual-hours ledger, local tag/version, `docs/checkpoints/C9.md` and retrospective.

**7. Definition of done:** The documented local product reproduces, critical failures are resolved or explicitly block release, workflow measurements and limits are reported, claims map to evidence, and the final pack is saved. No measured workflow gain is required to complete a valid negative study; usefulness remains unproven if not shown.

**8. What can go wrong:** Omitting setup time or failures, changing success criteria after observing results, treating a hosted demo as operational deployment, public release of assets without rights, or claiming recovery savings from a solo historical benchmark.

**9. Genuine blocker:** A critical geographic/provenance/reproduction defect prevents a usable release, or the study records are too incomplete to support its conclusion. A sound null workflow result is not a blocker to the case study.

**10. What to ask Codex:** Review checkpoint 9 release only: inspect actual repository/progress and evidence, reproduce one output, audit scientific/workflow/public claims, explain remaining limits, preserve history and update final state. Prepare material without publishing.

**11. Realistic time budget:** 25–35 hours. Learning 1–2; implementation 5–7; scientific analysis 5–7; testing 7–9; documentation 4–6; presentation 3–4. **Optional:** Public hosting, extra reviewers or extended user research only with a recorded scope/time decision. Preparing a release does not authorise external publication. See note 13 for cumulative totals and contingency.

**12. Record in the progress log:** Clean-run environment/result, defects and disposition, raw study/protocol IDs, paired measurements/quality failures, actual total/contingency use, final artifact/tag, release mode, rights decisions and unresolved claims.

**13. What can be shown publicly:** Permitted final code/artifacts, demo and case study after a deliberate publication decision. Report exact test scope and negative findings. A local release can be shown locally without any hosting claim.

**14. What must not be claimed yet:** Do not claim commercial usefulness, operational deployment, adoption, worldwide validation, avoided damage or cost savings unless separately demonstrated. Estimates are not actual effort.

**15. LinkedIn/showcase suggestion:** Topic: the actual end-to-end outcome. Evidence first: release + locked experiments + workflow comparison; visual: short evidence-led demo; supported: measured result under named conditions and actual local/hosted status; overclaim: “production-ready recovery system.” Employer review for affiliation/material; full source/model/asset/output review before release. See note 20 C9.
