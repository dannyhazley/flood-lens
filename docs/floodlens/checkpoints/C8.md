# Checkpoint 8 — Interactive map and analysis workspace

**1. Purpose:** Make the real outputs, their limitations and the inspection workflow understandable through a connected interface.

**2. Applied question:** Can a first-time reviewer inspect geographic evidence, flag verification needs and export a usable brief?

**3. Why this matters:** The surrounding workflow must help a user judge the evidence. Attractive layers without truthful state, uncertainty and provenance do not meet that purpose.

**4. Concepts before starting:** Vertical slice, map tiles/COG, raster display versus scientific grid, vector overlay, comparison eligibility, accessible states and frontend/service contract. Read notes 09/12.

**5. Exact ordered tasks:**

1. Phase A, 15–20 h: introduce React/TypeScript/Vite and MapLibre only now. Connect one eligible event/scene to an actual service run and result. Include a legend and known-coordinate check before expanding screens.
2. Benchmark a small scene and decide pregenerated local tiles/previews versus a raster server. Record provider/basemap rights and offline behaviour; do not load whole training collections into the browser.
3. Phase B, 15–20 h: add compatible baseline/model/reference comparisons, metric denominators, validity and confidence/coverage views. Clearly mark absent truth, raw versus calibrated probabilities and deterministic-method confidence unavailability.
4. Add the single approved/synthetic asset overlay, candidate inspection notes and human verification fields. Preserve geometry IDs/source dates and distinguish machine predictions from analyst annotations. Two scenes/dates may be compared descriptively; this is not validated inundation change.
5. Phase C, 15–25 h: connect submit/queued/running/failed/retry states and saved selections to real persistence. Add provenance panel and export bundle/brief; reopen downloaded outputs independently. Record the minimal timings needed by the frozen workflow study.
6. Phase D, 10–15 h: test complete success and unsupported/interrupted-input journeys using real outputs. Check keyboard access, focus, contrast, legend readability, map alternatives and empty/unavailable/error states.
7. Measure load/interaction behaviour on named scenes/hardware, fix confusing/high-impact issues, and record a captioned 60–90-second walkthrough including a poor result or failure. Stop feature expansion; the scored workflow study belongs to C9.

### C8 build guide — connect one real geographic journey, then expand

Use **React + TypeScript + Vite + MapLibre GL JS**, with the browser’s `fetch` and a small typed API module. Use npm with a committed `package-lock.json` and its clean-install operation in CI unless the repository already consistently uses another manager; ESLint supplies frontend linting, TypeScript’s compiler supplies the type check, and Vite supplies the production build. Add **Vitest/React Testing Library** for focused component behaviour if needed and **Playwright** for complete journeys. TypeScript describes expected shapes; the actual server contract/runtime validation still governs data. The user should not need to understand model internals to find dates, limits and verification needs.

#### Start with a small component/state plan

Proposed components are ScenePicker, RunStatus, MapWorkspace, LayerLegend, MethodComparison, ProvenancePanel, InspectionNotes and ExportPanel. They are responsibilities, not a demand for eight screens. Keep selected scene/run/layer state in the smallest common owner; do not introduce a global-state framework before ordinary React state is insufficient.

| Operation | Core API | Outcome / mistake to prevent |
|---|---|---|
| UI state and lifecycle | React `useState`, `useEffect`, `useRef` | Track selections/request state; clean up maps and polling to prevent duplicate work |
| Network | `fetch`, `AbortController` | Handle HTTP errors, loading, cancellation and stale responses; an old scene request must not overwrite the new selection |
| Map setup | MapLibre `Map`, load event, `remove` | Create once per intended mount and dispose on unmount |
| Geographic layers | `addSource`, `addLayer`, `setLayoutProperty`, `setPaintProperty` | Real aligned imagery/water/validity/asset layers, visibility and opacity |
| View/inspection | `fitBounds`, `queryRenderedFeatures`, event handlers | Frame the supported footprint and inspect asset IDs; display selection is not an analytical geometry computation |
| Component checks | Testing Library `render`, `screen.getByRole` and user interaction helpers | Loading/error/legend/export controls are understandable and accessible |
| End-to-end checks | Playwright `page.goto`, `getByRole`, `expect`, download event | Real select → job → map/report → export and failure/recovery journeys |

Keep the UI’s API client in one module with typed request/result shapes matching the service schema. Do not scatter URL construction/JSON assumptions across map controls. A clean service error should become an actionable message, not a generic “something went wrong” or infinite spinner.

#### Make the browser/service connection explicit

Create the Vite application under `web/` only now; keep npm’s lockfile and scripts for development, type checking, lint, tests and production build. Include MapLibre’s required stylesheet and give the map container an explicit height; a zero-height container can look like a data failure even when requests succeed.

Choose one API base path, such as `/api`, and document the actual local frontend/backend ports. Use a Vite development proxy to the backend and define whether the prefix is kept or stripped so it matches real routes. If deliberately calling across origins directly, configure FastAPI’s `CORSMiddleware` for the exact local frontend origin; do not use a broad wildcard as a substitute for understanding the request. Confirm one catalogue request in browser network tools before debugging map layers.

For the local production demonstration, serve built assets through a documented local route or static server. If the backend serves the SPA, keep `/api` routes distinct from the UI path and ensure the HTML fallback does not swallow API errors. Production build success alone is not proof the built app reaches the backend.

#### Choose a bounded geographic display path

For the first tiny north-up scene, a pregenerated image source with correct geographic corner coordinates may be sufficient. Transform scientific-grid coordinates to the map’s required geographic coordinates deliberately; do not pass projected metres as longitude/latitude. A simple image quad is a bounded demo approximation and can distort rotated/nonlinear grids. For supported larger/rotated cases, prepare properly reprojected raster display tiles. Keep native scientific GeoTIFFs as exports and keep display values out of scoring.

Set a maximum display resolution/size and benchmark a named scene. If pregenerated tiles meet that workload, stop. If not, justify COG/tile serving under the recorded performance budget. No library grants basemap rights; provide attribution and a no-basemap/offline failure option.

#### Build in this order

1. Run the API and show one real catalogue selection with acquisition date, task and quality. Display loading, empty and rejected states before adding map polish.
2. Submit one bounded job and poll its real persisted state with a sensible interval, proposed one to two seconds for the local demo. Stop polling on terminal state/unmount; avoid competing requests and fake percent progress.
3. Load one result’s footprint/source/water/validity with a clear legend. Check known coordinates against QGIS and the exported grid. Make unavailable different from dry and provide a text summary beyond colour alone.
4. Add baseline/model/reference comparison only when task, support and evaluation versions are compatible. Where labels are unavailable, show that fact, not zero error. Label raw/calibrated probabilities and missing deterministic-method confidence accurately.
5. Add the one approved/synthetic road layer and inspection notes. Preserve source dates/IDs; selecting a segment in MapLibre does not prove water overlap unless the backend’s declared rule generated that relationship.
6. Add provenance and export. Use real output links/downloads, then reopen an exported raster/table outside the application. Saved view selections and analyst notes should survive refresh within the documented local persistence scope.
7. Test stale responses: switch scenes while a request is in flight; the previous response must not replace the current map. Test backend unavailable, failed job, empty catalogue and missing confidence/reference layers.
8. Finish keyboard/focus/contrast/text clarity, map performance and the short real demo. Add only the timing/quality records required by the frozen workflow study.

**UI tests to elevate the project:** a user can reach controls by role/keyboard; unknown truth is not presented as a score; incompatible comparisons are prevented; failure messages include the run/stage and next action; exports retain the expected ID/version; refreshing a running job does not duplicate it. Avoid snapshot tests that merely freeze accidental HTML structure.

**CI now includes** a locked frontend install, TypeScript check, lint/component tests as selected, production build, and one Playwright smoke journey against a tiny synthetic/allowed backend fixture. Save failed screenshots/traces as short-retention artifacts, checking they contain no sensitive data. Browser tests with a mocked API check UI logic; retain at least one real service/pipeline integration journey before claiming the product is connected.

**Teaching/repetition exercise:** explain the difference between client state, persisted job state, immutable scientific output and analyst annotations. Implement/rehearse a second tiny selection→result view later with the same request/error/cleanup pattern. Reuse the pattern, not a map component whose geographic assumptions you cannot explain.


**6. Expected files and evidence:** `web/` application, typed service client, actual map layers and job/provenance/export views, browser journey checks, performance/accessibility notes, workflow timing records, demo recording, `docs/checkpoints/C8.md`.

**7. Definition of done:** Both journeys work across connected screens and actual backend results, layers align, comparisons are honest, analyst notes persist, exports reopen, and key loading/error/accessibility cases pass.

**8. What can go wrong:** A polished mock mistaken for real integration; map stretching or reprojection changing metric meaning; missing ground truth shown as zero error; uncertain and invalid regions sharing a misleading colour; spinner without recoverable state.

**9. Genuine blocker:** Geographic displacement, contract mismatch, lost annotations, unusable exports or inaccessible core journeys prevents inspection. Lack of decorative polish or cloud hosting does not.

**10. What to ask Codex:** Review checkpoint 8 only: inspect actual UI/API/progress, walk a real success/failure/export journey, explain unfamiliar map concepts, verify one exported result, preserve scope and update state.

**11. Realistic time budget:** 55–80 hours. Learning 6–9; implementation 28–40; scientific analysis 5–8; testing 10–14; documentation 3–4; presentation 3–5. **Optional:** Extra screen polish within remaining hours. Extra asset types, general GIS editing, accounts and mobile-native apps are outside the route. See note 13 for cumulative totals and contingency.

**12. Record in the progress log:** Connected capabilities versus mocks, exact tested scenes/run IDs, geographic checks, comparison rules, browser/performance/accessibility findings, actual hours, remaining defects and study readiness.

**13. What can be shown publicly:** A labelled local working-demo recording with real outputs, provenance and one limitation; show synthetic overlays as synthetic.

**14. What must not be claimed yet:** Do not claim improved ML accuracy because the UI is polished, validated change detection, measured analyst-time savings before C9, or deployment from a local demo.

**15. LinkedIn/showcase suggestion:** Topic: an interaction that helps assess evidence. Evidence first: journey tests + real recording; visual: confidence/provenance/export flow; supported: actual implemented local behaviour; overclaim: “improves emergency decisions.” Employer review for branding/content; data/asset/basemap rights review for recordings. See note 20 C8.
