# Checkpoint 4 — Unseen-event evaluation, failure analysis and confidence

**1. Purpose:** Test the frozen methods on unfamiliar events and describe where outputs deserve caution.

**2. Applied question:** What happens on reserved events, and do confidence signals help identify errors without hiding missing coverage?

**3. Why this matters:** The intended applied scenario encounters unfamiliar conditions. Good average overlap is insufficient if a new landscape fails confidently.

**4. Concepts before starting:** Final-test lock, macro event results, calibration, Brier score, reliability diagrams, uncertainty/retained coverage, distribution shift and small-sample limits. Read note 11 reliability rules before opening final results.

**5. Exact ordered tasks:**

1. Phase A, 4–6 h: audit final-test access and freeze candidate hashes, preprocessing, decision threshold, optional calibrator, metric conventions and example-selection rule. Fit any calibrator only on a designated development/calibration role; two development events cannot support unlimited selection and calibration.
2. Phase B, 8–12 h: run the frozen baseline and neural candidates on reserved events, save immutable predictions and event confusion counts, and compute all predeclared summaries. Record valid/invalid/withheld coverage; no tuning follows.
3. Only after primary results lock, consider optional published-split reproduction as a separate experiment if it replaces time in this checkpoint. Do not merge its learned weights or results with the primary untouched-test claim.
4. Phase C, 10–15 h: report probability reliability/Brier by event and error versus retained coverage. State raw/calibrated status, bin counts, threshold source and class prevalence. A deterministic baseline has no invented probability calibration plot.
5. Inspect good, representative and poor cases using the predeclared rule. Examine supported conditions such as shadow, built areas, vegetation and boundaries; identify hand-reviewed categories and keep causal explanations as hypotheses.
6. Phase D, 8–12 h: finish the model card and failure/limitations report. Report individual final events and matched baseline differences; do not manufacture worldwide confidence from correlated pixels.
7. If an execution/data defect invalidates results, preserve them with the reason, fix the defect and disclose the changed test status. A rerun after tuning on the errors cannot be called an untouched test. Choose the final artifact based on the predeclared development policy, not a newly optimised test threshold.

### C4 build guide — results you can audit by hand

Use saved probabilities/classes and references; do not retrain while interpreting final events. Build the report generator and plots on development/synthetic material first, then run the frozen final protocol. Keep final outputs read-only/versioned after lock.

#### Concrete library operations

| Task | API / method | What to produce and what it means |
|---|---|---|
| Event classification metrics | Reuse C2 NumPy confusion counts | Exact integer support/counts and matched baseline/model event rows |
| Probability quality | `sklearn.metrics.brier_score_loss` or explicit NumPy mean squared error | Mean (water probability − binary label)² over eligible pixels, separately by event; record binary-positive class and library options/version |
| Reliability bins | `sklearn.calibration.calibration_curve` plus explicit bin counts | Mean predicted water probability versus observed water fraction; show nonempty-bin populations and fixed binning |
| Coverage curve | NumPy confidence sorting/threshold masks plus existing metric/error functions | Error and eligible fraction retained under a frozen confidence policy; empty retained sets are unscorable |
| Plots | Matplotlib axes `plot`, `bar`, `imshow`, `savefig` | Event tables, diagonal-reference reliability plot, coverage plot and aligned case panels |
| Optional scalar calibration | PyTorch temperature/logit optimisation on designated calibration data only | Positive fitted temperature and separate fit/selection provenance; skip fitting if data/budget is insufficient |

Do not flatten together all final events and call that generalisation evidence. Pixel arrays can be flattened **within a declared eligible event** to calculate a score; the report must preserve the event-level unit and coverage. For reliability, show prevalence and class-conditioned behaviour because mostly dry pixels can dominate averages.

#### Build the report in order

1. Read the frozen artifact/config IDs and check that both methods used the same geographic support. Join outputs by scene/event IDs, not file order.
2. Validate probability range, finite values and class/mask encoding. Reuse metric edge rules; flag unscorable scenes/events rather than silently deleting them.
3. Aggregate confusion counts for each event without duplicate windows. Generate per-event IoU, precision, recall, F1, coverage and paired baseline differences; then the declared macro/pooled summaries.
4. Make reliability bins on eligible probabilities with a fixed policy, proposed ten uniform bins initially. Record bin populations; `calibration_curve` omits empty bins, so do not mislabel returned points as all ten populated intervals.
5. Compute retained-coverage/error summaries. A simple binary confidence proxy is the larger of P(water) and P(non-water); label it a score, not guaranteed error detection. Fix any operating cutoff on development/calibration data, then apply unchanged.
6. Select examples by the declared rule and render source/reference/prediction/error/validity panels with common grids. Include a poor result and annotate hypotheses, not invented causes.
7. Write the limitations and final-test access/correction record before preparing a showcase figure.

**Worked probability example:** probabilities 0.9, 0.8, 0.2, 0.1 and labels 1, 0, 1, 0 give squared errors 0.01, 0.64, 0.64, 0.01. Their Brier score is **0.325**. At a 0.5 water decision threshold, two of four predictions are wrong. If a confidence cutoff of 0.85 retains only the first/last cells, the retained predictions are correct but coverage is **50%**. That is not a free accuracy gain; half the eligible area now requires another route to review. This is a synthetic calculation, not FloodLens performance.

**Proposed project functions:** `score_event`, `reliability_table`, `coverage_table`, `select_failure_examples`, `write_evaluation_report`. Verify each on a synthetic case before connecting it to final data. CI can check counts/ranges/report completeness, while the final scientific run remains deliberate and frozen.

**Teaching/repetition exercise:** tell someone why a probability of 0.8 is not “80% proven correct here”, and why two reserved events cannot support a precise worldwide guarantee. Design the analogous report for a medical model with patients as groups; keep the same evaluation discipline but reconsider error costs and definitions.


**6. Expected files and evidence:** Frozen candidate manifest, final-test access log, immutable predictions and result CSV, per-event reports, reliability/coverage figures, `docs/model-card.md`, failure gallery, `docs/checkpoints/C4.md`.

**7. Definition of done:** Final comparison is locked and traceable, per-event performance/coverage and confidence limits are reported, a failure is analysed, and no test-driven selection is concealed. Useful confidence is measured rather than assumed; negative findings are allowed.

**8. What can go wrong:** Retuning after seeing final mistakes; presenting retained-only accuracy without coverage; pooled accuracy hiding poor events; calling softmax uncertainty calibrated; claiming that uncertain regions capture all errors.

**9. Genuine blocker:** Unrecoverable artifact mismatch, invalid references or a compromised protocol prevents the intended claim. A poor held-out result or unreliable confidence is a completed finding that narrows the capability.

**10. What to ask Codex:** Interpret checkpoint 4 without tuning: inspect locked runs and progress, verify one result/coverage calculation, explain confidence versus correctness and event sample limits, preserve negative findings and update state.

**11. Realistic time budget:** 30–45 hours. Learning 4–6; implementation 5–8; scientific analysis 12–18; testing 4–5; documentation 3–5; presentation 2–3. **Optional:** Published-split reproduction or extra robustness analysis only by explicit substitution and separate labels. It never becomes new selection evidence for the same final-test claim. See note 13 for cumulative totals and contingency.

**12. Record in the progress log:** First final-test access date, frozen IDs, events/counts, all results including failures, confidence policy and fit source, invalidated runs/reasons, human/compute hours and claim limits.

**13. What can be shown publicly:** Locked event scores with event count, a permitted informative failure and coverage curve. Link every number to the exact report.

**14. What must not be claimed yet:** Do not claim global reliability, calibrated new-event confidence without evidence, forecasting, operational readiness or improved model performance that the results do not support.
