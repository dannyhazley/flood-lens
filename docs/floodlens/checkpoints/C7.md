# Checkpoint 7 — Service contracts, job state and product workflow

**1. Purpose:** Expose the proven local analysis through a bounded, truthful service and design the two user journeys.

**2. Applied question:** Can an analyst request work, understand its state, recover from failure and obtain a traceable inspection result?

**3. Why this matters:** Long analysis cannot be represented by a successful HTTP response alone. Durable state and clear contracts make a wider integration possible.

**4. Concepts before starting:** API/contract, typed schema, background job, durable state, idempotency, cancellation, vertical slice and decision-value protocol. Read notes 09/10/12.

**5. Exact ordered tasks:**

1. Phase A, 8–10 h: sketch successful-inspection and unsupported/interrupted-input journeys using real C5 outputs. Define catalogue, workspace, comparison and export states; label mockups design. Keep one asset type and local single-user scope.
2. Specify request/status/result/error schemas with approved scene/model IDs, resource limits and stable job IDs. Define comparison compatibility and output/provenance fields before adding screens.
3. Freeze `docs/decision-value-protocol.md` using note 09: identical manual/assisted packets, brief rubric, quality failures, time/throughput/consistency/uncertainty/overlay/reproduction/report measures. Pilot on development/demo material and set a numeric worthwhile-change criterion before scored runs.
4. Phase B, 12–18 h: introduce FastAPI/typed models and wrap the existing pipeline. Implement bounded submission, status and result retrieval with one small local worker. Keep numerical code in the shared package.
5. Validate missing/unknown/incompatible input and file/resource limits. Define duplicate-submission/retry behaviour. Do not fetch arbitrary supplied URLs or claim requests are complete before output validation.
6. Phase C, 5–7 h: persist jobs and analyst/run references in SQLite (rasters remain files). Exercise queued → running → succeeded/failed/cancelled, restart interruption, deliberate retry and supported cancellation. Document any cancellation limits.
7. Run contract/state tests and a real valid job plus invalid request. Save the agreed screen scope, state transition evidence and workflow-test protocol; do not build the whole UI yet.

### C7 build guide — API plus a durable, bounded worker

Use **FastAPI + Pydantic + Python `sqlite3` + one local worker process** as the starting design. Add HTTPX/TestClient for service checks. The API validates/submits/reads; the worker calls the C5 package; SQLite records state and references; geographic files remain in run directories. This avoids long requests and duplicated scientific logic.

#### Define the small service surface

| Route / object to implement later | Input | Response / rule |
|---|---|---|
| Scene/method catalogue | Filters limited to approved inventory | IDs, acquisition/bands/task/quality and compatibility metadata; no arbitrary local-file browsing |
| Submit analysis | Approved scene IDs, method ID, options/schema version and request key | HTTP accepted response with stable job ID/state; no fabricated completed raster |
| Job status | Job ID | queued/running/succeeded/failed/cancelled, stage, timestamps and readable warning/error |
| Result | Successful job ID | Complete output manifest and bounded download links; unfinished work returns explicit not-ready status |
| Cancel | Supported job ID/state | Cancellation request or final cancelled state; distinguish these truthfully |
| Retry | Failed/interrupted job reference | New attempt linked to prior failure; do not erase the failed job |

A Pydantic `BaseModel` declares fields/types; `Field` expresses length/range constraints; `field_validator` checks domain compatibility where a simple type is insufficient; `model_validate` checks parsed input and `model_dump` produces a serialisable record. Keep scientific validation in the shared package rather than only these web models. A string scene ID can be well-typed and still refer to an unsupported scene. FastAPI `HTTPException` provides deliberate error responses; expose stable reason codes rather than raw tracebacks. A starting status policy is 202 for accepted work, 404 for unknown job, 422 for invalid request fields, 409 for an incompatible/not-ready state and 200 for retrieved status/result metadata; document the policy and test actual responses before client integration.

#### Build the persistence and worker contract

Use `sqlite3.connect`, parameterised `execute`, transactions and explicit commit/rollback. Do not interpolate user values into SQL. Store job ID, request key, immutable request/config/hash, state/stage, creation/start/end times, attempt link, worker ownership, output-manifest path and error code/message. Store analyst notes separately from immutable predictions.

1. Validate the request and insert a queued job transactionally before acknowledging it. Make the request key unique within the intended scope; repeating it returns the existing compatible job rather than duplicated processing.
2. Have one worker claim a queued job in a transaction using a conditional state change. Confirm it actually claimed the row before work starts. A database transaction should be short; do not hold it open during inference.
3. Call `analyse_scene` with the resolved approved inputs. Persist useful stage updates. Stop only at documented safe cancellation boundaries.
4. Mark succeeded only when the complete, verified output manifest exists. Map known pipeline exceptions to stable service errors and a failed state.
5. On restart, reconcile old running jobs with completed manifests/worker ownership. If safe recovery is not implemented, mark them interrupted/retryable and preserve files; never leave permanent “running”.
6. Constrain job count, scene dimensions/bytes, worker concurrency and output storage. Local single-user mode does not justify unbounded resource consumption.

Do not implement a subprocess-per-request or rely solely on FastAPI `BackgroundTasks` for heavy durable jobs. Its callback facility is useful for small response-following tasks, but it does not itself provide the persistent state/restart guarantee you need. Do not add Celery/Redis unless measured requirements justify another service.

#### Core tests and expected observations

| Check using `fastapi.testclient.TestClient` / HTTPX and temporary SQLite storage | Expected observation |
|---|---|
| Valid submit | Accepted job ID persists and later reaches the real complete result |
| Unknown/mismatched scene/method | Specific validation failure; no phantom queued success |
| Repeat request key | Same compatible job returned, no duplicate output writer |
| Worker exception / full-disk fixture | Failed stage and reason persist; result is not downloadable as success |
| Restart while running | Interrupted/reconciled state and deliberate retry, not a spinner forever |
| Cancel queued/running | No start for queued cancellation; running only cancelled after safe stop |
| CLI/API same scientific input | Same task/classes/grid/mask and numeric tolerance, differing only in run metadata |

**Proposed project functions:** `validate_analysis_request`, `enqueue_job`, `claim_next_job`, `execute_job`, `reconcile_interrupted_jobs`, `get_result_manifest`. Test numerical package behaviour separately from HTTP/state behaviour. Use a stub worker for quick route/state tests and one tiny real pipeline integration test; a stub alone does not prove the package is connected.

**Freeze the human-task study now:** implement the note 09 pilot on non-scored development material, set the numeric worthwhile-change criterion and quality rubric, and save the protocol. Fix task packets/order/time rules before the final study; do not let an attractive UI result choose the criterion later.

**Teaching/repetition exercise:** draw the request → persisted job → worker → complete output → status path and explain what a process crash changes at each arrow. Reuse the same pattern for a video conversion or report-generation service; replace the domain computation while retaining explicit state/failure semantics.


**6. Expected files and evidence:** API schema/OpenAPI, service wrapper, job-state table/store, worker limits, state transition tests, journey sketches, `docs/decision-value-protocol.md`, `docs/checkpoints/C7.md`.

**7. Definition of done:** Real bounded jobs run through stable contracts and durable state, restart/error/retry paths are truthful, output links resolve, two journeys are scoped, and the decision-value protocol is fixed before scoring.

**8. What can go wrong:** Business logic duplicated in endpoints; in-memory-only status; orphaned running jobs after restart; duplicate writes; fake progress percentages; mocked screens called integrated; workflow criteria chosen after results.

**9. Genuine blocker:** A state/contract defect loses work or marks incomplete outputs successful; service and CLI disagree on the same inputs; request limits cannot be enforced. No accounts/multi-tenancy is expected.

**10. What to ask Codex:** Review checkpoint 7 only: inspect real contracts/jobs/progress, verify one complete and one failed/restarted job, explain states and boundaries, preserve pipeline behaviour and update handoff.

**11. Realistic time budget:** 25–35 hours. Learning 4–5; implementation 12–18; scientific analysis 2–3; testing 4–5; documentation 2–3; presentation 1. **Optional:** External queue/server only if measured concurrency demands it and scope is revised. One worker and SQLite are the default. See note 13 for cumulative totals and contingency.
