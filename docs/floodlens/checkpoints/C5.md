# Checkpoint 5 — Dependable geospatial inference workflow

**1. Purpose:** Turn the scientific result into one repeatable source-to-output analysis that can sit inside another system.

**2. Applied question:** Can another engineer produce a geographically correct, traceable water layer and use it in a bounded inspection example?

**3. Why this matters:** A map has limited decision value if coordinates, provenance, failures or exports are wrong. This is the first complete applied vertical slice.

**4. Concepts before starting:** Model artifact, inference contract, georeferenced output/GeoTIFF, separate inference versus evaluation masks, provenance, vector overlay, atomic completion and reproducibility. Read architecture note 10.

**5. Exact ordered tasks:**

1. Phase A, 8–10 h: define one supported command for approved scene/list → validation → shared preprocessing → selected-method inference → output → report. Reject incompatible bands, units, grid/task or untrusted artifact; start with local approved IDs, not arbitrary URLs.
2. Process bounded windows if needed. Preserve output grid, validity and declared probability/class meaning; avoid duplicate overlap counting and visible seams. The inference mask must not require ground-truth labels.
3. Phase B, 8–12 h: write and reopen class/probability/validity rasters. Compare CRS, transform, dimensions, mask and known pixel-centre coordinates. Inspect a landmark/footprint in independent GIS. Calculate area only with an appropriate metric-area method and record units.
4. Test missing bands, incompatible units, all-invalid input, malformed geography and interrupted output. Publish a complete result manifest only after every required output validates; leave failed/partial runs clearly failed. Measure runtime/memory/disk on named hardware/workload.
5. Phase C, 9–13 h: choose one small permitted road corridor/asset layer, or clearly labelled synthetic geometry. Record source date/rights/CRS. Use one explicit intersection rule to show candidate inspection segments, including uncertain/unobserved areas; no automated damage or safe-routing decision.
6. Create a simple report, QGIS project or small viewer with real imagery/output, a legend, asset overlay, provenance, human verification requirements and exports. Do not start the full service/UI now.
7. Reproduce the command from a clean environment with approved assets or a tiny distributable fixture. Save a success and rejection demonstration and the standalone case-study report.

### C5 build guide — a command another system can trust

The selected method may be the baseline. Make both baseline and neural artifacts obey one result contract, while recording when probabilities/review scores are unavailable. The command takes approved scene ID(s), model/method ID, configuration and output directory, not an uncontrolled bag of arrays.

#### Functions and library boundaries

| Responsibility | APIs to use | Result / check |
|---|---|---|
| Parse a bounded command | Standard `argparse`; `pathlib.Path` | Validated named arguments, clear help and nonzero failure exit; no hidden vault paths |
| Resolve/load | Existing manifest/hash functions and model artifact loader | Approved exact files and trusted artifact with matching task/bands/units |
| Windows when needed | `rasterio.windows.Window`, dataset `read`, `window_transform` | Bounded input chunks with correct spatial identity and a declared context/edge policy |
| Neural execution | Shared `preprocess`, module `eval`, `torch.inference_mode`, `sigmoid` | Same numerical result path as experiments; baseline calls its existing prediction function |
| Geographic writing | `rasterio.open` in write mode, dataset `write`, `write_mask`, `update_tags` | Class/probability rasters with copied/explicit grid and task/run metadata |
| Round trip | `rasterio.open`, array equality/tolerance, `xy` / `index` | Reopened values, CRS, transform, bounds and masks agree with the contract |
| Vector context | `geopandas.read_file`, `to_crs`, geometry validity and intersection operations; Shapely where needed | One permitted/synthetic road layer expressed on a compatible grid/CRS |
| Water geometry when needed | `rasterio.features.shapes` on valid water cells | Georeferenced class polygons for a bounded intersection, preserving the transform and excluding unavailable cells |
| Runtime/atomic output | Standard `time.perf_counter`, `tempfile`, filesystem rename/finalisation, JSON manifests | Measured stages and a complete result marker; incomplete bundles remain visibly incomplete |

Never use GeoPandas `set_crs` as a coordinate conversion: it assigns an interpretation to existing coordinates. `to_crs` transforms known coordinates. Likewise, a raster’s CRS label and its affine transform must both describe the actual stored grid.

#### Build and verify the first whole-scene path

1. Specify the output roles and encoding. For example, class codes 0=non-water, 1=water, 255=unavailable in a uint8 GeoTIFF, with a separate validity mask. Probability, if available, uses float values with an explicit unavailable convention and mask. These are proposed output encodings, not assumptions about source label codes.
2. Run one small supported whole scene before adding windowing. Preserve CRS, transform, dimensions and valid support. Save the scalar/configuration facts needed to reproduce the result.
3. Write to a temporary run directory. Reopen everything and check values, geometry and manifest file list; finalise only after validation succeeds. A JSON state saying success before files close is a defect.
4. Add one incompatible-input and one interrupted-write test. Confirm the error code/message names the failed stage and prior valid outputs stay intact.
5. Open the resulting GeoTIFF in QGIS: add the layer, inspect layer properties/source CRS, compare the known study footprint and at least one identifiable location, toggle validity and read a pixel value. A visually correct basemap overlay does not verify numerical class accuracy.
6. Add one permitted/synthetic road layer. Validate its CRS/source date and geometry. Derive candidate intersection segments under a stated rule and measure lengths only in suitable metric coordinates. If vectorising water makes too many tiny polygons, constrain the study area; do not build a large general GIS engine.
7. Export candidate IDs, overlap/status, uncertain/unobserved flags, source dates and verification notes with the result. No-overlap is not safe-road status.
8. Package a readable report and machine-readable manifest with exact hashes, method, warnings, observation time, geographic checks and links to the original output files.

**Windowing decision:** if the supported scene already fits memory, keep the whole-scene path for the first release. If not, add windows with overlap/context padding; write each output core exactly once and declare how edge predictions are handled. Compare whole-scene versus windowed output on a small fixture and inspect seams; neural padding can make them differ, so do not promise identical values without a measured tolerance/policy. `window_transform` is required when exporting a cropped window as its own raster.

**Proposed project functions:** `analyse_scene` orchestrates existing components; `validate_input_contract` rejects incompatible inputs; `predict_scene` preserves class/probability/validity roles; `write_output_bundle` controls finalisation; `validate_output_bundle` reopens/checks; `build_candidate_inspection_table` handles the single context rule. The API later calls `analyse_scene`, not a second implementation.

**Diagnosable execution:** use standard `logging.getLogger` and stage records containing run ID, method/config/source IDs, stage start/end, duration, warning and stable failure code. Save the concise record alongside `run.json`; do not dump raw arrays or private paths. A novice should be able to identify whether failure occurred in validation, prediction, writing or geographic verification without rereading all source code.

**CI additions:** synthetic export/reopen, mask/nodata encoding, known coordinate, malformed input and interrupted-bundle tests. Do not make CI depend on a basemap or raw source download. A disposable fixture can test geometry with known answers and no redistribution ambiguity.

**Teaching/repetition exercise:** trace a downloaded geographic output back to its input hashes and producing method without opening the browser. Explain what a future integrating government system can consume and why it still needs asset currency, domain rules and field verification. Reuse this package→contract→portable-output pattern on another analytical project.


**6. Expected files and evidence:** Inference configuration/entry point, model contract, GeoTIFF outputs + validity/probability where supported, `run.json`, readable/JSON report, output checksums, road source record or synthetic fixture, candidate segment table, reproduction instructions, `docs/checkpoints/C5.md`.

**7. Definition of done:** A clean local run produces valid geographic outputs and report, malformed input fails usefully, output provenance is complete, one bounded overlay works, and downloads reopen in independent GIS. Synthetic overlay proves integration only.

**8. What can go wrong:** A PNG posing as a geographic output; map display interpolation affecting metrics; inference validity depending on labels; partial files looking successful; road overlap presented as closure/damage; arbitrary remote input fetching.

**9. Genuine blocker:** Coordinates/masks cannot survive export, preprocessing differs from experiments, or the artifact cannot be reproduced. Lack of a live API or cloud host is not a blocker for this local slice.

**10. What to ask Codex:** Validate checkpoint 5 only: inspect actual code/progress, verify one raster round trip and failure, explain CRS/masks/provenance, preserve work, keep the asset exercise bounded and update state.

**11. Realistic time budget:** 25–35 hours. Learning 3–4; implementation 10–14; scientific analysis 2–3; testing 6–8; documentation 3–4; presentation 1–2. **Optional:** A COG or minimal API only if needed to inspect the slice and substituted within the timebox. Full service belongs to C7; extra asset types remain deferred. See note 13 for cumulative totals and contingency.

**12. Record in the progress log:** Input/model/code/config IDs, output hashes, independent geographic checks, fixture/real-asset status and terms, runtime/memory, failed cases, actual hours and exact reproduction command.

**13. What can be shown publicly:** A clean-run recording, georeferenced export reopening, one permitted/synthetic overlay and a useful failure message, labelled local prototype.

**14. What must not be claimed yet:** Do not claim deployment, adoption, road safety/damage, new inundation or speed savings from a single pipeline timing.
